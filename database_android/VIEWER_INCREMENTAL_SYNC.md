# 両サイト・両閲覧ページの差分同期

対象：メルヘン（幸町・長町南）、P-STATION（P’s CUBE）の自分用閲覧ページ・共有ページ。2026-10-13の利用者指定「実現できるかを限界まで検討し、可能なら両方」「はい、両サイト・両ページ」。画面・採点・取り込みの競合規則は変えない。

## 結論と差分になる範囲

Webアプリでも、端末に取得済みの日別データを保存すれば差分通信ができる。実装では **変更した日だけ** を新しい閲覧用ファイルとして出力し、Web側も変更したパーツだけを取得する。1日が1MiBを超えると、その日の中をさらに分割する。初回は全パーツが必要。

| 処理 | 今回の動作 |
| --- | --- |
| 入力バックアップ | 既存どおり新規・更新されたファイルだけ読む。ただし新しい全期間JSONの中身は全件読む |
| Google側の統合 | 既存の蓄積とPC出力を読み、既存規則で全体を統合・検査する |
| 閲覧用出力 | 内容が変わった日別パーツと小さい更新一覧だけを書く |
| 自分用・共有ページの通信 | キャッシュにない／壊れたパーツだけ取得する。変更なしならパーツ取得0件 |
| ブラウザ内のデータ処理 | パーツを全件の従来形式に戻して既存の検証・画面へ渡す。IndexedDBキャッシュは全体を1トランザクションで保存 |
| PCへ戻すP’s CUBEバックアップ | 全期間の `pscube-backup-cloud.json` を従来形式で保持。新しい入力時の全件出力は残る |
| PCアプリ自身の書き出し | 従来どおり全件。次のクラウド同期で日別版を再生成する |

「すべての処理が台単位の差分になった」という意味ではない。Androidの書き出し自体を台単位にするには、取得時の変更履歴、端末固有の連番、受信確認、取り消し、全件への復旧をPC・Androidにも導入する必要がある。全件バックアップの互換と復旧経路を守りながら行う別の移行になる。今回の対象である閲覧用出力・Web読み込みは、そこまで変えずに対応した。

## 比較した方式

1. **全件JSONの一部を書き換える**：Driveのメディア更新はファイル内容を送るAPI。JSON内の台のキーを指定する更新ではない。HTTP PATCHという名前でも台単位にはならない。
2. **全件＋台単位の追記ログ**：通信は小さくなるが、消した台の印、順序、重複、ログ圧縮、端末が長く離れた場合の再取得、PCの全件出力との世代照合が必要。復旧と運用の複雑さが大きい。
3. **日別の置き換え**（採用）：日付で自然に区切れ、数値訂正・台の消失・期間落ちもその日の完成形で扱える。1台変更でも同日のパーツは送るが、変更のない過去の日は送らない。

Googleのファイル更新仕様：[Drive APIのアップロード](https://developers.google.com/workspace/drive/api/guides/manage-uploads)。Web保存が消える場合がある根拠：[WebKitのStorage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/)。Googleの実行時間・通信等の制限：[Apps Script quotas](https://developers.google.com/apps-script/guides/services/quotas)。**48MiBは本プロジェクトの安全上限であり、Google Drive自体の保存上限ではない。**

## 保存形式と故障時の動作

- 「database共有」直下に `database-viewer-parts-meruhen.json` / `database-viewer-parts-pscube.json` を置く。一覧にはサイト・元PCファイルのIDと版・見出し・各パーツのSHA-256、日付、件数、バイト数、内部のDrive IDを保存する。
- パーツ名は `database-viewer-part-サイト-SHA256.json`。UTF-8で最大1MiB。並びとオブジェクトのキー順を正規化して、同じ内容なら同じハッシュになる。
- 書く順番は既存の蓄積／全期間バックアップ → 新しいパーツ → 更新一覧。途中の失敗では旧一覧を維持し、次回は保存済みの蓄積からやり直す。未使用の完成パーツは再利用する。
- 読み取り側は更新一覧に載ったパーツだけを返す。任意のDrive IDは受け付けず、クライアントに内部IDを返さない。ハッシュ・バイト数・日付・件数を検査する。1回のパーツ取得は最大8個。
- `?check=1` は従来の `drive-check` に更新一覧を追加する。旧Webページからの通常GETには、パーツを連結して従来形式の全件JSONを返す。自分用・共有用とも同じ読み取り処理を同梱する。
- クライアントのキャッシュは **スクリプトURL＋サイト** ごと。両ページのIndexedDB `database-viewer-parts-v1` に保存。全部取得・検査できてから1回で保存し、失敗時は前のキャッシュを維持する。壊れた／無くなったパーツは再取得する。保存領域が使えない場合も、その回の表示はできるが次回は再取得する。
- 共有ページは取得中の世代変更時に一覧から1回再試行する。自分用ページは失敗として従来データを保ち、次回更新で一覧を取り直す。
- PCが元の全件ファイルを書き直した場合、その版と合わない日別一覧は使わない。一時的に新しいPC出力を読み、次のクラウド同期でAndroidの蓄積を反映した日別版に戻る。PCとGoogleの共通ロックはないため、同時更新を完全に直列化する保証はない。
- 6時間おきに、現在の一覧から参照されていない、更新から7日を超えた生成パーツだけをごみ箱へ移す（1回最大200個、失敗は次回）。元バックアップ・PC出力・蓄積・イベント・🌈は整理対象外。旧版を大量生成する運用では整理が追いつかない場合がある。Driveのごみ箱を含む容量とApps Script実行時間は引き続き確認する。
- 有効な閲覧データ全体の48MiB／10万件、一覧1MiB、1台1MiBの上限を保持する。分割は現在の集約処理の容量上限をなくす変更ではない。Google側での所要時間・iPhone実機の体感速度は未検証で、わかりません。

## 手元の実データを読み取りだけで測定

2026-10-13、`database/data/` のコピーを集計。内容を公開・変更・Googleへ送信していない。

| ファイル | 記録数 | 日数 | 元のバイト数 | 最大1日分のJSON配列 |
| --- | ---: | ---: | ---: | ---: |
| database-viewer.json | 20,454 | 35 | 19,131,405 | 965,665 |
| pscube-viewer-drive.json | 4,956 | 17 | 2,934,179 | 177,982 |

1日分だけが更新される例なら、元の全件JSONの約5.0%／6.1%＋更新一覧の転送量になる見込み。ただし表は空白を除いた日別配列の集計で、実通信の圧縮・JSON応答のエスケープ・見出し・Googleの待ち時間を含まない。速度が同じ割合で速くなるという測定結果ではない。

## 導入順序（順番を守る）

差分出力は配布状態では **false（従来方式）**。読み取りスクリプトを先に更新しないと、更新前のスクリプトは古い全件ファイルを表示する。

1. **Web側は2026-10-14に公開済み**（自分用 `b1b56bb`、共有 `0edca42`）。再公開する場合は、検証済みの自分用Webページ・共有Webページを公開する。公開ステージは `tool/stage_viewer.py` / `tool/stage_share_viewer.py` を通す。ページの接続先や実記録は公開しない。
2. **自分用**の既存Apps Scriptへ `tool/viewer_drive_script.gs` 全文を貼り替え、デプロイ管理 → 編集 → 新バージョンで更新する（URLを維持）。
3. **共有用**の既存Apps Scriptへ `tool/viewer_drive_script_readonly.gs` 全文を貼り替え、同様に新バージョンで更新する。イベントへの書き込みを拒否する従来の制約は維持。
4. メルヘンの30分同期プロジェクトへ `tool/meruhen_cloud_sync.gs` 全文を貼る。上部の `MERUHEN_INCREMENTAL_VIEWER` を `true` にして保存、`syncMeruhenCloud` を実行する。
5. P-STATIONの30分同期プロジェクトへ `tool/pscube_cloud_sync.gs` 全文を貼る。`PSCUBE_INCREMENTAL_VIEWER` を `true` にして保存、`syncPscubeCloud` を実行する。
6. 両ページを再読み込みし、両サイトの既知の台・日付・数値を確認する。初回は全日分の取得。以後、1日分を追加したときに `showMeruhenCloudStatus` / `showPscubeCloudStatus` のログ「今回の差分出力」で更新パーツ数・KBを確認できる（戻り値の `status.incremental.parts` / `bytes` にも記録）。

差分モード中、従来名の閲覧用JSONはPCの入力基準として残り、Googleによる新しい統合結果は日別版に出る。Driveから旧名JSONを手動ダウンロードしても最新の統合結果ではない。旧名ファイルは削除しない。PCへ戻す方法はこれまでどおり、メルヘンは元のAndroidバックアップ、P-STATIONは `pscube-backup-cloud.json` を読み込む。

### 戻す／復旧する

- 従来方式へ戻す：各同期の `*_INCREMENTAL_VIEWER` を `false` にして保存し、そのサイトの同期関数を実行する。全件ファイルを書き直すため日別一覧は版不一致になり、読み取り側も全件方式へ戻る。Web・読み取りApps Scriptは新版のままでよい。
- 日別ファイルを消した・壊した場合：`rebuildMeruhenViewerParts` / `rebuildPscubeViewerParts` を実行する。処理済み入力の全再取り込みではなく、保存済み蓄積から閲覧用を作り直す。
- `database-backup-android-20261012-064105.json` の48MiB超による未取り込みは今回の差分化では解決しない。別途、PCで取り込むか、元アプリから必要な期間を小さく書き出す必要がある。取り込めない記録の中身はこの作業では確認しておらず、わかりません。

## 開発・試験

共通ソース：`tool/viewer_parts_core.js`、`viewer_parts_drive.js`（読み取り専用）、`viewer_parts_publish.js`（同期用）、`viewer_parts_client.js`（Web用）。`node tool/build_viewer_parts.mjs` で配布GS4本とWebモジュール2本へ反映。P’s CUBEの既存生成器からも同じ同期部品を取り込む。

`test_viewer_parts.mjs` は出力確定順・復旧・ハッシュ・キャッシュ・上限・旧形式互換・読み取り許可範囲を検証。既存の両同期試験に差分モードの統合試験を追加。`test_viewer_parts_browser.mjs` は実ブラウザと実IndexedDBで両サイト・両ページの「初回2日 → 更新した1日 → 再読み込み0日」を確認する。Googleの応答には合成データを使用し、実Google・実iPhoneの確認とは区別する。

検証結果（2026-10-14）：Web公開前の全ゲート52項目ALL PASSED（PC273＋93、Flutter584、JS45本・223件、analyzeエラー警告0／info21）。実保存ページの検査は `PSCUBE_ARCHIVE_DIR` がなくSKIP。公開URLで両サイト・両ページの差分試験と共有画面試験PASS、配信18ファイルが公開commitと一致・seed4パス404。その後のGS閲覧ログ条件補正は関連73件PASSで別途確認済み。Google側の差分モード有効化・実iPhone速度は未確認。
