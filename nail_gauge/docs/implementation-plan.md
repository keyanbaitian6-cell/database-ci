# 釘間隔の推定 実装計画（nail_gauge）

作成：2026-10-31 Claude（計画のみ。アプリ本体は未実装）
関連：[design.md](design.md)、[measurement-validation.md](measurement-validation.md)

## 1. 方針

- 小さく動くものを積み上げる。各タスクの終わりに、試験か実機で「動いた」と言える状態にする。
- 計算・座標（純Dart）を先に作り、試験で固める。カメラ・画面はそのあと。誤差の検証（V0〜V3）が済むまで、段階3の自動化に手を付けない。
- 既存の `database_android` の作法（`ChangeNotifier`、`sqflite`、`flutter_lints`、日本語の文言、試験は `test/` に置いて `flutter test` で流す）に合わせる。

## 2. PCで開発を始めるときの最初の作業

1. **T0の決定を利用者に確かめる**（CIの分数に関わる。下のT0）。
2. このPCの Flutter（2026-10-31時点で 3.47.1 stable を確認）で、リポジトリの最上位から：
   ```
   flutter create --org <利用者が決める> --project-name nail_gauge --platforms android nail_gauge
   ```
   - 既にある `nail_gauge/docs/` は残る（`flutter create` は既存のファイルを消さないが、実行前にフォルダの中身を確かめる）。
   - 生成された `README.md` は、この計画への案内に書き換える。
3. `analysis_options.yaml` を `database_android` と同じ形（`flutter_lints`、`build/**` 等の除外）にする。
4. `flutter analyze` と `flutter test`（雛形の試験）が通ることを確かめ、雛形の試験は消すか置き換える。
5. Android実機をUSBでつなぎ、`flutter run` で雛形が起動することを確かめる。

## 4. 意味のある単体試験

「通ること」だけでなく、過去に起きやすい誤りを捕まえる試験にする。

- 基本式：玉 200画素・対象 170画素・11.0mm → 9.35mm。玉と対象を入れ替えると値が変わる（引数の取り違えを捕まえる）。
- 単位：基準直径を11.0から11.02に変えると、推定値がちょうど 11.02/11.0 倍になる。玉に対する比は変わらない。
- 円の当てはめ：既知の円の円周の点（全周・半周・90度の弧）。3点が一直線で `circle_degenerate`。
- 無効：点が画像の幅ちょうど（`x = W`）は有効、`x = W + 0.01` は `point_outside_image`。同じ点2つで `ball_zero`。
- 座標：EXIF 6 と 8 を取り違えると落ちる試験（縦長の画像の左上の印が、右上・左下のどちらに行くか）。表示用の縮小 s を掛け忘れると落ちる試験（s ≠ 1 で往復）。
- 保存：再計算で古い結果が残る。測定を消しても、他の測定が使う画像は残る。画像のSHA-256が変わった記録は点を描かない。
- 集計：外れ値は印だけで、自動で除外されない。違う日付は別の集計になる。
- 画面：結果画面に「信頼度」「誤差±」の文字が出ない。初期の基準直径が「11.0mm（公称値）」と出る。

## 5. 実機で確かめること

- 権限：初回の許可・拒否・「今後表示しない」・設定からの許可・使用中の取り消し。
- ライフサイクル：撮影中のホームボタン・画面の消灯・通話の着信・別のカメラアプリの起動からの復帰。撮影画面を離れたらカメラが解放される。
- 画像：縦持ち・横持ちで撮った画像の点が、履歴から開き直しても同じ位置。端末の画像（他のカメラアプリで撮ったもの、スクリーンショット）の読み込み。
- 重さ：最大解像度の画像の読み込みにかかる時間、その間に画面が固まらないこと、ルーペの描画がなめらかなこと。メモリが足りない端末での動き（大きな画像を続けて開く）。
- 保存：アプリを入れ直す前に、端末内のデータがどう扱われるかを利用者に伝える（アンインストールで消える。書き出し T11 で残せる）。

## 6. 自動化（段階3）へ進む判断条件

次がすべてそろったら、段階3の検討を始める。

1. V0が通り、V1・V2・V3を標準条件で実施して、結果を記録している。
2. [measurement-validation.md](measurement-validation.md) §7 の判断で、「mmで表示を続ける」か「相対比較に切り替える」かが決まっている（どちらでも段階3には進める。計画を止める判断なら進まない）。
3. 手動で点を置く位置の決まり（どの縁に置くか）が定まり、V2で人の揺れが分かっている（自動検出の目標を「人と同じくらい」と言えるため）。
4. 自動検出の評価用に、手で点を置いた写真が、調整用・検証用に分けて十分な数（目安【仮】それぞれ30枚以上）ある。
5. 自動化で何を楽にしたいか（玉の指定、釘頭の指定、撮るタイミング）を利用者と決めている。

進む順の案：

1. 手で置いた点の近くだけを探す「吸着」（玉の縁・釘頭の縁に点が寄る）。純Dartで試し、遅ければネイティブ／OpenCVを検討（[design.md](design.md) §D-9）。
2. 確認画面での、玉・釘頭の候補の自動表示（手で直せる）。
3. プレビューでのぼけ・玉の有無の判定と、自動撮影。
4. 測定箇所の追跡。

各段階で、自動の点と手の点の差、真値との差を、検証用データで測ってから次へ進む。

## 7. 運用の注意

- PCでの開発中も、push の前に `nail_gauge` の `flutter analyze` と `flutter test` を流す。T0で (a) を選んだ場合、CIは `nail_gauge` を試験しないので、手元の試験が唯一の確認になる（`nail_gauge` の試験をCIに足すかは、分数を見せて利用者に聞く）。
- APKを作る・端末に入れるのは、利用者が依頼したときだけ。作ったら版と導入の状況を `AI_COLLABORATION.md` に記録する。
- 店で撮った写真・実データはGitHubに上げない。
