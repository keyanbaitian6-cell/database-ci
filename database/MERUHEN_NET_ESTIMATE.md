# メルヘンの推定差枚（2026-10-04）

利用者の依頼「追加の通信なしの推定差枚で構わないので実装」。メルヘン長町南店・幸町店の差枚を、保存済みのグラフ座標と最大持玉から計算して表示する。**確定差枚ではない**ため、画面では必ず「推定差枚」「（推定）」と書き、P’s CUBEの確定差枚（`net_medals`）とは別に扱う。保存形式・採点・MY・最大持玉は変更しない（保存はせず、表示のたびに計算する）。

実装：PC `database/core.py` の `meruhen_net_estimate`、Android・閲覧ページ `database_android/lib/meruhen_net.dart` の `meruhenNetEstimate`（同じ規則。保存済み11,806件で両者の結果が全件一致することを確認）。

## サイトの事情

- 差枚の数値は返らない：`machine_detail` の `sadama` は null、`slump_data` の復号後は `svg` だけ、`slump_data_old` は空。
- SVGはサーバーが描く。高さ400でゼロ線200.5、上端20.5・下端380.5（上下180px）。高さを変えて要求すると上下は (高さ−40)/2 px になり、同じ倍率で描かれる（実機で高さ4000を1回確認）。

## 規則（推定）

- 縦軸の片側の幅 R 枚は 1,000・2,000・4,000・6,000…（以降2,000刻み）のうち、その日の振れ幅 max|値| が収まる最小の段階。
- 最大持玉は「谷から山までの最大の上がり幅」。
- 値＝（200.5−Y）×R÷180。推定差枚＝終点の値（グラフは毎日0から始まる）。

R の決め方：
1. 振れ幅がその段階に収まり、1つ前の段階には収まらない（半ピクセルの丸めは許す）。
2. 線の全座標があるとき：最大持玉÷（線で測った上がり幅×R/180）が0.98以上になる最大の段階（点が間引かれているので比は1以上に出る）。
3. 4点（ゼロ・山・谷・終点）しかないとき：上がり幅の下限（時刻順の4点で測った値。山・谷の時刻が無い古い記録は始点→山）と上限（山−谷）から、最大持玉が [下限×0.98−1目盛り, 上限×1.3＋1目盛り] に入る段階が1つだけのときに限る。
4. 決まらない・最大持玉が無い（10万超の異常値を含む）・高さ400以外のSVG → 推定しない（空欄。0にしない）。一日中ゼロ線上 → 0。

## 根拠（2026-10-03の調査）

- 保存済みグラフ約6,200件で、最大持玉÷上がり幅が R/180 の位置に鋭い下限を持つ山に分かれる（各段階の下位1%が R/180 の0.996〜1.005倍）。2店舗とも同じ。
- 推定差枚を機種ごとに BIG・REG・回転数で当てはめると、マイジャグラーV BIG 239〜243・REG 103〜107・1回転−1.20〜1.21（R²0.97）など、ノーマル機として自然な係数。グラフと別の項目からこの係数が出るので、倍率と符号の裏付けになる。
- 実機（長町南615番台・2026-10-03）：高さ400と4000で終点の比が一致。高さ4000の座標で+1,421、高さ400で+1,422。
- 詳細：リポジトリ外の `a/work/outputs/meruhen-investigation/REPORT_20261003_claude.md`。

## 限界

- サイトのコード（サーバー側）での証明や、正解の差枚との照合はない。
- 誤差：1ピクセルの丸めで ±R/360 枚（R=2,000で約±6、10,000で約±28）。R を取り違えると2倍・1.5倍の誤りになり得る（規則で一意に決まる台だけ出すことで減らしている）。
- 対象：保存済み11,806件（閲覧用）のうち、全座標では10,270件、4点だけ（Androidアプリの一覧）では6,729件を推定できる。全座標と4点の両方で推定できた6,372件のうち食い違いは1件。
