# Cookie変更後の既存動作の再検討（2026-10-02）

利用者の依頼：これまでの動作に影響がないか再検討する。
最新main `44ffa13` を取り込み、メルヘンとP’s CUBEのAndroid・PCの変更を再確認した。
通常操作の回帰テストでは新たな失敗はない。ただし、下記3点に影響の可能性があり追加修正した。

## 追加で修正した点

1. 同じURLを渡すだけの再試行では、ネイティブブラウザの再読み込みが保証されない。PCはpywebviewの公開load_urlでURL・準備状態を更新し、WebView2の現在のSourceと同じならCoreWebView2.Reloadを明示的に呼ぶ。異なるページからの復帰は従来のload_url。Androidも現在のURLが同じ文書ならreload、異なるエラー文書ならloadRequestを使う。現在URLの照会待ちで画面を閉じた場合は通信しない。
2. 台別ページの選択日付がfragmentだけで変わった場合、最後のNavigationStartingのURLを再試行すると以前の日付へ戻る可能性がある。PCは同一文書の現在URLを採用し、Androidは現在文書をreloadすることで選択したfragmentを保持する。別店舗・別機種・別台・別クエリへ勝手に再試行先を変えない。
3. HTTP拒否の応答でも、サイトの本文に認証・同意の操作が含まれる可能性がある。PCはHTTP応答をアプリのエラーHTMLで置き換えず、そのまま表示して操作可能にする。DNSなど本文を読み込めなかった通信失敗だけ専用のエラー画面を使う。HTTP拒否時の自動OFFと新しい保存の拒否は維持する。

さらに、pywebview 6.2.1のbefore_loadは同期イベントであるため、PCメルヘンは再読み込みのUI呼び出し中にAutoCaptureのロックを持たないよう修正した。その間の別の再試行・ON・保存開始を抑止する。P’s CUBEのネイティブコールバックも、自動取り込みのロック処理を作業スレッドへ移し、通常の読み込み完了後に接続エラー状態を解除する。

## 維持する動作と意図した変更

- 既存のDBスキーマ、保存済み数値・グラフ、採点、バックアップ形式、店舗/機種/日付の選択、次ページへの進め方は変更しない。
- 再試行ではCookie・認証状態・SQLite記録を消さない。保存済みのデータとCookie設定の保持は継続する。
- 通常の認証・同意画面では既存の待機処理を使う。主ページや対象通信がHTTP拒否を返した場合はOFFにするため、ここは従来の「ONのまま待機」と異なる意図した変更。サイトの認証画面は操作可能なまま残す。
- 再試行は自動OFF、保存・確認中は拒否。既に開始した保存は完了まで待つ。明示的なCookie消去は既存の確認付き操作のみ。
- 広告・別ページのHTTP失敗、過去の読み込み完了は現在の通信失敗へ混ぜない。
