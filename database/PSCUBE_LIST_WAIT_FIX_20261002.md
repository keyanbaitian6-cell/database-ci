# PC P’s CUBE：全台表示が遅いページでの待機修正

2026-10-02、利用者がPC版の停止を報告。OFF→ONと全台表示で一度復帰した後、再度停止。
添付画面は「表示は6台、設置台数は31台」と「同じページで3回失敗したため待機中」を表示していた。
これは台数不一致で保存を拒否した後の自動待機。ウィンドウ全体のフリーズとは区別する。
調査開始のmainは `96b9a700f1e0d76320d9ee4f96e72b136490c191`。

## 再現と変更

- 従来のPCスクロール処理は、台数が6回（各350ms、約2.1秒）変わらないと終了する。
  6台だけ先に出し、残り25台の追加に3秒かかる疑似ページでは、修正前の試験が `6 != 31` で失敗した。
  実サイトで何秒の遅延・どのイベントが起きたかは未確認。この試験は同種の早い読み取りを再現したもの。
- 全台一覧では、保存済み機種一覧から現在のURLと一致する設置台数を読み取り専用SQLite接続で取得する。
  別機種・貸玉・店舗の台数を流用しない。欠損DBを作らず、未知・競合する台数は推測しない。
- 台数が短時間安定しても、既知の設置台数未満ならスクロールと待機を継続する。
  利用者の追加指定に従い、各機種の全台一覧の取得ごとに毎回ページの一番下までスクロールする。
  350msの待機を最大70回とする制限は維持。機種一覧・台別ページと台数不明時は既存の扱いを維持。
  読み取り前後のページ同一性も確認する。
- 保存時の設置台数一致チェック、3回失敗の待機、PC初期7.1秒、台別取得は維持。
  Android本体・バージョン・APKは変更しない。Android/tool内の2スクリプトはPCのJS回帰テスト。

## 確認

- PC P’s CUBEのPython65件成功（一時DB）。設置台数のURL照合、別貸玉・別店舗、DB非作成、DB不変も確認。
- Chromium：スクロール回帰とPCカード回帰成功。別々の2機種ページで各回6→31台の遅延表示後に31台を渡して保存・台別へ移動。
  実サイトへの要求は疑似内容で応答し、外部通信は遮断。
- 実WebView2 `154.0.4258.48`：`tests/smoke_pscube_delayed_list.py` 成功。
  一時DBから設置31台を取得し、6台から3秒後に31台へ増えるインラインページで本番スクロールを実行。
  31台まで待ち、一時DBのSHA-256不変を確認。利用者の窓・Cookie・記録は操作しない。
- ログ：作業フォルダの `outputs/pc-pscube-31-cards-*-20261002.log`。
  修正前の失敗ログも `pc-pscube-31-cards-before-20261002.log` に保存。
- 修正後の実サイト31台取得は未実施。台数が制限時間内に揃わなければ保存は拒否する。

ソース `a53e8d1` をmainへ反映してPC配布一式を再ビルド（BuildTag `pscube-list-wait-20261002`）。
`smoke_frozen_runtime.py` で生成3EXEの内蔵コード/JS/DLL一致、メインから両補助EXEの実WebView2起動、
新しい設置台数APIの公開を確認。配布先は `database/bin` の3フォルダ一式。Androidの再ビルドは行わない。

利用者のP’s CUBE窓は既に読み込まれたPythonソースを実行しているため、閉じて開き直すと修正が反映される。
一時DBの不変は確認したが、検証期間に利用者側のP’s CUBEのDBと2閲覧JSONの更新があったため、
利用者データのSHA-256不変とは報告しない。原因は未特定。生成EXE検証のDB引数が一時ディレクトリであることは確認した。
